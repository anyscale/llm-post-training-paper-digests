ABSTRACT

Reinforcement learning (RL) has driven substantial progress in coding agents by relying on
verified successful trajectories as learning signals. However, such trajectories are scarce in
long-horizon software engineering tasks, where a minor error can invalidate the entire rollout.
Repeatedly restarting from the initial state is commonly used yet inefficient, and resetting
only the context with working directory misses state changes such as installed dependencies.
Therefore, branching from intermediate steps to preserve earlier progress requires restoring
both the agent context and execution environments. In this paper, we present SPROUT
(SnaPshot-based RollOUT), an agentic RL rollout framework that scales long-horizon coding
tasks by resuming and branching from intermediate states. Specifically, SPROUT was built
on top of a lightweight infrastructure that checkpoints both the filesystem and the agent
context after each assistant turn. A verifier-guided backtracking policy then selects where to
resume a failed attempt and how to proceed. Extensive experiments on long-horizon coding
tasks show that SPROUT achieves up to 23.6% improvement over pass@k across various
LLMs, while using 32–52% of their tokens. For RL training of Qwen3.8-27B, SPROUT stably
outperforms standard GRPO by 13.9 points on three long-horizon coding benchmarks while
cutting the time per training step by 39.5%. SPROUT thus makes RL on long-horizon coding
tasks both more effective and cheaper to scale.

1 Introduction
Coding agents are becoming capable of completing increasingly long tasks in real software environments, such as resolving issues in large repositories (Jimenez et al., 2024; Yang et al., 2024b; Huang
et al., 2026a). For such tasks, reinforcement learning with verifiable rewards (RLVR) has become the de
facto training paradigm (Shao et al., 2024a; He et al., 2026a; Wu et al., 2026): the agent attempts a task
in an executable environment, a verifier such as the task’s test suite checks the final result, and the
policy is updated from these outcomes. Such training is especially expensive on long-horizon tasks. A
single attempt may read a large, unfamiliar codebase, install dependencies, build artifacts, and run
test suites, and it can take hours to finish.

receives credit only if its final solution passes. Over a long attempt, one wrong decision anywhere, such

2024a), a task whose attempts all fail has zero advantage for every attempt and contributes no gradient.

Two strategies are commonly used to obtain more positive signal. The first samples more attempts per
task (Brown et al., 2024b; Li et al., 2022), which multiplies an already high cost: every new attempt
redoes its exploration and setup from scratch and can repeat the same mistake. The second branches
from intermediate steps of earlier attempts. In a coding environment, this requires three things. The
restored environment must match the agent’s context at the branch point, including the files the agent
edited, the packages it installed, and the artifacts it built anywhere in the system. Checkpoints must
be cheap enough to take at every step, since any step may turn out to be the right place to branch. The
branch point itself must also be chosen well. Existing methods miss at least one of these requirements.
Tree search and reflection methods (Yao et al., 2023a; Zhou et al., 2024; Shinn et al., 2023), as well
as CBPO (Wang et al., 2026a), branch only within the conversation. Among RL methods that restore
sandbox states, Shepherd (Yu et al., 2026) versions only the agent’s workspace, BPO (He et al., 2026a)
snapshots containers only at a few selected steps, and both rely on layered container snapshots with
hard limits on depth. Full virtual machine snapshots are complete but must store guest memory at
every step, making the storage requirement unacceptable on long horizon tasks. To choose branch
points, BPO uses policy entropy without consulting the verifier, and Shepherd delegates the choice to
a stronger external model. Their RL experiments focused on tasks normally take 8 - 25 steps, leaving
long horizon unexplored.
In this paper, we present SPROUT (SnaPshot-based RollOUT), an agentic RL rollout framework
that scales long-horizon coding tasks by resuming and branching from intermediate states. Sprout
is composed of three components: 1) a restorable execution layer runs each attempt in a microVM
(Agache et al., 2020) and take a snapshot of its filesystem incrementally after every assistant turn,
pairing each checkpoint with the matching agent context. 2) a verifier-guided backtracking policy
decides where to branch (Figure 3): the actor itself reviews failed trajectories with the verifier’s
feedback, chooses where to resume, and proposes the first action of the new continuation, so the
recovered trajectories do not import knowledge from a stronger model. 3) a GRPO-based training
procedure learns from the branched rollouts and distills the guidance used during search into the base
policy.

2 Related Work
Long-Horizon Coding Agents. Coding agents solve software engineering tasks by interleaving
reasoning with tool calls in interactive environments (Yao et al., 2022; Dong et al., 2024; Wang et al.,
2024). Frameworks such as Mini-SWE-agent (Yang et al., 2024a), OpenHands (Wang et al., 2025),
OpenCollab (Hsu et al., 2026), and Claude Code (Anthropic, 2025) let them navigate repositories, edit
code, and validate changes through execution, and benchmarks such as SWE-bench Verified (OpenAI,
2024), SWE-bench Pro (Deng et al., 2025), DeepSWE (Huang et al., 2026b), and Terminal-Bench
2.1 (Merrill et al., 2026) evaluate them on increasingly long-horizon tasks. A single attempt can span
tens to hundreds of tool calls and fail on a single error, after which it is usually discarded and
resampled from scratch, redoing progress such as understanding the repository and localizing the
root cause. SPROUT instead resumes failed attempts from intermediate states and reuses their prior
progress.
Tree Search and Backtracking. Repeated sampling increases task coverage but restarts every sample
from the initial state (Brown et al., 2024a; Jiang et al., 2025). Tree-search methods instead expand
and backtrack over intermediate states (Yao et al., 2023b; Hao et al., 2023; Zhou et al., 2023), much
as Go-Explore first returns to a visited state and then explores (Ecoffet et al., 2021), while reflection
methods correct errors in later attempts using verbal or tool feedback (Shinn et al., 2023; Gou et al.,
2024). In software engineering, SWE-Search (Antoniades et al., 2025) applies Monte Carlo tree search
to issue resolution, and Shepherd (Yu et al., 2026) delegates the choice of where to intervene over
reversible traces to a stronger external model. Because agents edit files, install packages, and build
artifacts, branching only within the conversation, as tree search and reflection methods do, leaves the
environment inconsistent with the agent’s context, and Shepherd versions only the agent’s workspace.
SPROUT restores the full filesystem together with the matching agent context and lets the actor itself,
rather than a stronger model, use verifier feedback to choose where to branch and how to continue.

Stateful Sandboxing and Agentic RL. In sparse-reward agent tasks, groups whose attempts all fail
are common and yield no gradient under group-relative methods such as GRPO (Shao et al., 2024b).
Several RL methods therefore branch from intermediate states, including VinePPO (Kazemnejad et al.,
2024) for advantage estimation, TreeRL (Hou et al., 2025) for process supervision, SPARK (Wu et al.,
2026) at critical states identified by the agent’s own decision signals, CBPO (Wang et al., 2026b) for
contrastive branching, and BPO (He et al., 2026b) with container snapshots. However, most of these
methods branch only within the conversation, which in coding environments leaves the environment
inconsistent with the agent’s context, while BPO can resume only from a few steps selected by policy
entropy without consulting the verifier, so neither approach supports consistent branching from an
arbitrary tool boundary. Among checkpointing mechanisms (Wang and Zheng, 2026; Li et al., 2025;
Xu et al., 2025), layered container snapshots (Merkel et al., 2014) have hard limits on depth and full
microVM snapshots (Agache et al., 2020) must store guest memory at every step. SPROUT checkpoints
the full filesystem incrementally after every tool call and pairs each checkpoint with the matching agent
context, so any tool boundary can be restored with low storage overhead and without re-executing the
prefix, enabling more efficient exploration to obtain learning signals.

3 SPROUT
SPROUT is a rollout framework for long-horizon agentic tasks, it allows resuming execution from any
recorded intermediate state of an earlier attempt and explore alternative continuations from that state.
We first formulate the rollout collection problem and give an overview of the framework. We then
describe the execution layer that enables resumption and the verifier-guided backtracking policy that
determines where to resume and how to continue. Finally, we present policy optimization with the
resulting rollouts.

turn. After t completed turns, the agent is at boundary t with joint state st = (et , ht ), where et is the

The central capability of SPROUT is local access: a search procedure can return to an earlier joint state

This interface separates execution from search. The execution layer makes recorded states available for
isolated continuations, and a replaceable search policy decides which states to revisit and whether
to give guidance when start the continuation; randomized branching, heuristic selection, and tree
search all fit the same interface. An archive A x stores the resulting execution tree for task x, including
checkpoint handles, parent links, contexts, and verifier feedback, and T x denotes the multiset of its
completed attempts. New outcomes in the archive inform further search, and completed attempts are
organized into training groups.
3.3 Restorable Execution States

Consistent Continuation Boundary. Local access requires the environment and the agent context to
describe the same point of an attempt. Boundary t of τi is eligible, t ∈ E (τi ), if a filesystem checkpoint
was taken after all tool calls of turn t completed and the conversation prefix can be recovered up to
and including the observation ot . Search branches only from eligible boundaries, so every continuation
starts from the observations and execution state of its selected prefix. Any guidance for a new
continuation is stored separately from that prefix.
Filesystem restoration under the harness contract. Each attempt runs in its own microVM (Agache
et al., 2020), so a checkpoint covers the whole guest filesystem, including dependencies and build
artifacts outside the working directory. Our harness executes every tool call as a synchronous shell
command and disallows background processes, so by the end of a turn no process started by the agent
is still running, and all state that persists across turns lives on disk. Restore therefore boots a fresh
microVM from the saved filesystem and reinitializes the tool runtime, and guest memory never needs
to be captured. Together with the recovered context, this gives the continuation the full state of its
prefix under the stated harness constraints.

Incremental checkpoints and isolated branches. After each turn, the execution layer records the
changes to the VM disk as an incremental block-level OverlayBD layer. Consecutive checkpoints share
all unchanged content, so the storage a checkpoint adds grows with the blocks written during the turn
rather than with the size of the environment. Each restored branch writes to its own copy-on-write
layer over the saved history, so several continuations can inherit the same progress without affecting
one another or their parent. Incremental storage and isolated writes together make it practical to
checkpoint every turn of a long trajectory.
3.4 Verifier-guided Backtracking Policy

Restoration makes earlier states available; the search policy decides which of them are worth continuing
from. We instantiate it with verifier-guided backtracking, in which the actor πθ also analyzes failures
and plans branches under separate role prompts. The roles share parameters, and only the analysis
and planning roles see feedback from completed attempts, so no separate analyst or reviewer model is
involved.
From failure evidence to branch decisions. For each newly failed attempt τi , the policy writes
an analysis zi of why the attempt failed, which of its progress can be reused, and which eligible
boundaries could plausibly lead to a successful continuation. These candidates are hypotheses about
where recovery is possible; they need not identify the first incorrect turn. In round r, a reviewer prompt
reads the archive, now including these analyses, and plans up to Kr branches:

3.5 Policy Optimization with Branched Rollouts

Training reuses the same restoration and repair mechanisms to construct groups. During search, the
reviewer sees diagnostics that never appear in the actor’s ordinary context. Training aims to transfer
the resulting corrective behavior into the actor while accounting for the prefixes that trajectories in a
group share.
Constructing training groups. Each task receives a fixed-size group: two independent roots and
K = 3 retained children per root, for eight evaluated attempts. This specializes the collection framework
to a single layer of children. If at least one root succeeds (TT or TF), the reviewer selects one usable
boundary per root, and that root’s children continue from it without an injected starting turn. If
both roots fail (FF), the reviewer uses verifier feedback to rank boundaries and attaches a corrective
direction to each. A starting turn is then written from each visible prefix and its direction, filtered by a
judge, and executed in the restored environment before the actor continues. A boundary is usable only
if it is eligible and its prefix leaves room for the continuation within the context budget. Algorithm 1
(Appendix B) specifies the oversampling, independent-rollout fallbacks, and task replacement that
keep every group at eight attempts.
Learning without the review context. For a guided branch, the learner sees the retained prefix, the
starting turn, and the executed continuation, but not the diagnostic analysis or the corrective direction.
The policy is therefore trained to produce corrective turns from the context it has during ordinary
execution. Removing the review context from the learner’s input does not remove its influence on how
the sample was generated. We therefore treat the objective below as a clipped surrogate that distills
guided behavior into the actor, not as on-policy optimization over samples from the unassisted actor.

4.4 Scaling: Depth vs. Breadth

We compare single-round branching with iterative review-and-branch using GPT-5.6 Luna on DeepSWE (Figure 4). A configuration R × B allows up to R review rounds with B branches per round. All
configurations reuse the same baseline rollout for each task; the baseline resolves 52 tasks, leaving
61 for branching. An analyst summarizes each newly failed trajectory with its verifier verdict, and
a reviewer combines the accumulated analyses to select B checkpoints and write continuations. The
actor resumes from the corresponding snapshots and conversation prefixes. Each round executes all B
branches, and the search stops at the end of the first round with a verifier pass. For single-round scaling, we randomly permute each failed task’s 32 accepted branches once and retain the first B branches
for B ∈ {1, 2, 4, 8, 16, 32}, yielding nested subsets without replacement. Token totals include the shared
baseline once and the actor, analyst, and reviewer calls attributed to each setting; single-round subsets
include the selected actors and all recorded usage of the original 32-branch analyst/reviewer once.
Depth improves token efficiency. Breadth saturates quickly: one branch lifts the baseline from 46.0%
to 68.1%, but widening from 1 × 4 to 1 × 32 raises the resolve rate only from 75.2% to 77.9% while
recorded tokens grow from 0.57B to 1.85B. Across the comparisons at maximum branch counts of 2, 4,
and 8, allocating more rounds increases the resolve rate and reduces accounted token use. With an
eight-branch maximum, 1 × 8, 2 × 4, 4 × 2, and 8 × 1 resolve 76.1%, 85.8%, 89.4%, and 91.2%, using
745.2M, 673.6M, 566.7M, and 525.7M tokens, respectively. The two extremes recover 34 and 51 of the
61 initially failed tasks. Even 2 × 1 reaches 80.5% with 465.5M tokens, exceeding 1 × 16 at 77.0% and
1.10B tokens. These results compare the fixed single-round subsets with the recorded multi-round
runs.
Sequential depth limits intra-task parallelism. The token-efficiency advantage of depth comes with
sequential dependencies: each review round requires trajectories and verifier feedback from the
10

SPROUT: Scaling Agentic Reinforcement Learning for Long-Horizon Software Engineering
preceding round. Branches within a single round can, in principle, execute concurrently, potentially
reducing per-task latency. Intermediate configurations such as 2 × 4 and 4 × 2 therefore trade off
feedback depth against intra-task parallelism. Our current implementation executes branches within
each round sequentially, so the reported results characterize the success–token trade-off and do not
measure the latency achievable with parallel branching.

5 Conclusion
In this paper, we have proposed SPROUT (SnaPshot-based RollOUT), a framework that addresses
the scarcity of verified positive trajectories in long-horizon agent learning by resuming failed rollouts
from any intermediate snapshot. Combining copy-on-write filesystem checkpointing, step-aligned
conversation restoration, and verifier-guided backtracking, it lets agents backtrack to an earlier state
and reuse the trajectory up to that point rather than re-executing it from scratch. Across multiple
models and coding benchmarks, SPROUT matches or exceeds repeated independent sampling at
a fraction of the token cost, and in RL training it improves the base policy on all benchmarks
while outperforming GRPO with shorter training steps. By transforming failed rollouts into costeffective starting points for exploration, SPROUT provides a practical foundation for collecting positive
supervisory signals and scaling autonomous agent capabilities.

A Experimental Setup and Supplementary Experiments
Benchmarks and models. We use the 113-task public DeepSWE, the 89-task Terminal-Bench 2.1, and
the 51-task SWE-bench Pro v2 Hard. Sampling experiments use Kimi K3, Qwen3.8-27B, Claude Sonnet
5, DeepSeek V4.1 Flash, and GPT 5.6 Luna with fixed model weights. Kimi K3 runs with reasoning
effort set to max, and all other models run with reasoning effort set to high. In SPROUT, the actor also
performs failure analysis and branch selection under separate role prompts, with the same reasoning
effort as its actor role.
Execution environment. All runs use mini-swe-agent (Yang et al., 2024b) with a sandbox shell as the
environment interface. Shell calls are synchronous, and background processes are disabled. SPROUT
checkpoints the full filesystem after each turn and pairs it with the corresponding agent context. Each
branch resumes in an isolated sandbox. DeepSWE attempts run offline with 2 CPUs, 8 GB of memory,
and a time limit of 10,800 seconds.
Baselines. Independent sampling performs four fresh attempts per task. Pass@1 is the mean resolve
rate across the four passes, and Pass@4 is the fraction of tasks solved in at least one pass. We also
evaluate Shepherd (Yu et al., 2026) with its own fork-selection procedure and an entropy-based variant,
which selects branch points using policy entropy and is only evaluated with Qwen3.8-27B that can
expose token log-probabilities in our setup.
Collection protocol. For each model and benchmark, a single-attempt pass over all tasks provides
the parent attempts. SPROUT branches from the failed parents, restoring each selected checkpoint
together with its step-aligned agent context, and a task counts as solved if its parent or any of its
branches passes the verifier.
Reported metrics. The sampling comparison reports resolve rate, recovery rate, total execution
steps, and total tokens. The resolve rate counts tasks with at least one verified success. Token totals
combine input and output tokens and are expressed in millions.We report normalized recovery as
( Rmethod − RPass@1 )/(1 − RPass@1 ), measuring the fraction of the remaining performance gap beyond
Pass@1 recovered by each method.

B Training Algorithm
Algorithm 1 details one SPROUT training iteration for a single task x. Two independent roots are
first sampled from s0 and graded, and their outcomes determine the mode of the group: TT if both
succeed, FF if both fail, and TF otherwise. Each root τi then grows a family of K children from its
15

SPROUT: Scaling Agentic Reinforcement Learning for Long-Horizon Software Engineering
usable boundaries Bi , namely the eligible boundaries (Section 3.3) whose prefix leaves at least ∆ tokens
of headroom within the context budget L. In TT and TF groups, the reviewer selects one boundary
per root, and all children of that root continue from it without an injected starting turn. In FF groups,
the reviewer analyzes the archive, including verifier feedback, and returns ranked boundaries tk ,
each paired with a corrective direction gk . The policy then writes a starting turn a′k at each boundary
from the visible prefix and gk alone, without access to the analysis or the verifier feedback, and a
judge filters the resulting turns. Each child restores the environment and context at its boundary in
a fresh sandbox, executes its starting turn if it has one, continues under the current policy, and is
graded. Each family launches O extra children so that stragglers do not delay the iteration, and only
the first K children to complete evaluation are retained. A task with a family that has fewer than K
completed children is replaced. The eight retained attempts are credited and masked as in Equation 7
and contribute to one policy-gradient step (Equation 8).

C Starting Turns versus User Hints
A guided branch needs some way to carry the corrective direction into the restored context. We
considered two formats.
User hints. The simplest format is a user hint: an external message, appended to the restored context,
that states the corrective direction. Because the hint is derived from verifier feedback, it tends to
leak into the continuation. The actor often recites the message, quotes test names or expected values
from it, or justifies later actions by referring to it, so the continuation depends on information that is
unavailable during ordinary execution. The hint also causes a problem for training. It is not an action
of the policy and must be removed from the learner’s context. Once it is removed, the training context
no longer explains the continuation: turns that recite or respond to the hint remain in the trajectory
without a visible cause.
Starting turns. SPROUT instead writes the guidance as a starting turn a′j in the actor’s own voice,
consisting of brief reasoning followed by tool calls whose observations come from real execution
(Section 3.4). The turn must read as a natural continuation of the prefix and may not mention
checkpoints, other branches, or hidden tests, and in training groups a judge filters turns that violate
these constraints (Appendix B). The context therefore contains no foreign message. During training, a′j
remains in place as an ordinary policy turn, and only the review context used to write it is removed
(Section 3.5). The actor thus learns the corrective action itself rather than how to respond to an external
hint.

D State Projection and Cache Matching Efficiency
Motivation. In agentic reinforcement learning for long-horizon coding tasks, rollouts frequently
traverse identical or semantically equivalent intermediate states (e.g., repository navigation, virtual
environment configuration, dependency installation). Re-executing these initial setup steps from scratch
wastes compute budget, while naively snapshotting and restoring complete microVM environments
can introduce severe I/O contention. To amortize rollout overhead, SPROUT incorporates a statematching mechanism that identifies whether an intermediate execution state can be directly resumed
from an existing checkpoint. This appendix provides a detailed empirical comparison of our state
projection approach against representative caching and hashing baselines.

Analysis and Key Takeaways. Table 7 highlights the latency-coverage trade-offs across different
state-matching paradigms:
1. Brittleness of Textual and Graph Matching: Exact full history matching yields an extremely low
hit rate (0.8%) because trivial non-deterministic variations in tool outputs (e.g., timestamps, process
IDs, temporary directory names) invalidate string identity. Similarly, while TVCACHE’s TCG
tracks tool call trees, it misses many reusable states (3.2% hit rate) due to subtle command-line
syntax variations in long bash command sequences.
2. The Overhead Bottleneck of Deep Hashing: Full-workspace hashing achieves the theoretical
upper bound hit rate of 36.7% (reducing retained tasks from 134 to 38). However, traversing and
hashing multi-gigabyte repository workspaces incurs an average online latency of 79.1 ms per
checkpoint check. In high-throughput parallel rollout environments where hundreds of microVMs
execute synchronously, this overhead causes severe CPU and disk I/O contention.
3. Optimal Latency–Coverage Balance: Our Scan-free Relaxed Projection strikes a practical balance: it
achieves a 14.1% overall hit rate (20.6% on Luna queries) while requiring only 0.201 ms of online
latency—over 390× faster than full-workspace hashing. Crucially, all matched states achieve 100%
precision, ensuring that branched continuations never inherit corrupted or mismatched filesystem
states.
4. Model-Dependent Trajectory Divergence: Across all caching methods, trajectories generated
by GPT 5.6 Luna exhibit significantly higher hit rates than Qwen (e.g., 20.6% vs. 6.2% under
our method, and 47.8% vs. 23.2% under workspace hashing). Luna follows more standardized
repository inspection patterns, producing reusable environment states during early setup stages.
